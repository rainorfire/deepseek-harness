# architecture-refactor-review

审视架构重构方案与实现落地是否一致，输出分级改良报告。

## 触发
用户给出一份技术方案/重构 plan（.plan.md / ARCHITECTURE.md / README 目标架构），并指向对应代码库，要求「从专业角度审视方案与实现」「看下有没有改良的地方」「评审落地质量」「方案与实现是否一致」。

## 方法（五步）

1. **先读方案建立承诺清单**：把方案的 todos / 承诺（常为 P0-Px 或分阶段）逐条列出，这是后续每一条的核对基准。
2. **并行 Explore 子代理深挖**：按模块切分（如 engine 核心 / gateway+frontend / 退役残留+部署依赖），每个子代理带足背景（目标架构、需验证的承诺点），要求返回 file:line 证据。
3. **亲自核实关键疑点**：子代理结论不可全信——亲自 Read 最重的判断（如手写路由、中间件、工厂装配），并核对 git log 中可疑提交（如「移除 X 后端」这种与方案声称方向相反的提交）。
4. **跑测试验证「可测」承诺**：说测试加固完成的，实际跑 `pytest`（macOS 无 timeout 命令，直接跑即可）。报告 100 passed 这类结果。
5. **出分级报告**：已兑现（表格：承诺→证据→判断）/ 硬伤（🔴 按优先级）/ 中优（表格）/ 小问题（顺手清）。

## 评审要点（经验清单）

- **文档与实现互相打脸的信号**：注释写 fail-closed、代码实际 fail-open（如 visibleRoles 空=公开）——这是最危险的，必须抓。
- **「标准协议」可能是私有方言**：前端解析的是 UPPER_SNAKE_CASE 私有事件，只在两端自洽，不标准——多端接入时每个端都要重写。
- **关键能力是黑盒**：Team 等核心工具靠 `pip install -e` 外部源码，仓库内零实现——编译期不可见、CI 不可复现。
- **退役干净度**：源码零残留 ≠ 干净，还要查 `__pycache__` 残留旧字节码、未调用端点（如 /hitl/resolve）、死参数、兼容回落。
- **信任链**：header 注入的 user_id 无验签、端口需内网隔离。
- **可观测性半成品**：只有 basicConfig 无 tracing/otel。
- **配额/限流的承诺 vs 实现**：架构文档写了职责，代码可能是零。
- **测试覆盖缺口**：方案说 session replay / HITL resume / 模板热更新 / Team 委派都要测，实际可能只有热更新一个测试。

## 输出格式
- 总评一句话（方案是否真实落地 + N 块硬伤）。
- 「已兑现」表格：方案承诺 | 落地证据(file:line) | 判断。
- 「硬伤」🔴 逐条：问题→位置→改良建议。
- 「中优」表格：问题 | 位置 | 改良建议。
- 「小问题」清单。
- 结尾问用户：要不要落成任务清单，或针对某个🔴给具体改法。
