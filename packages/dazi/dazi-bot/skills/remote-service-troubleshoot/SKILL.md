# 远程服务运维排查技能

## 适用场景

本技能适用于以下远程服务运维场景：
- Java后端服务的线上错误排查
- DSF分布式服务框架的调用问题
- 日志分析与异常定位
- 定时任务异常诊断
- 性能问题与超时问题分析

---

## 6步排查流程

### 第一步：问题分类与判定

根据用户提供的信息，判断是否需要查询线上日志：

| 需要查日志 | 不需要查日志 |
|-----------|-------------|
| 线上报错、异常堆栈 | 纯代码逻辑问题 |
| 特定时间点的错误 | 已知错误但不确定原因 |
| 关键字监控告警 | 代码审查发现的问题 |
| 用户反馈的线上问题 | |
| 性能/超时问题 | |

### 第二步：信息收集

**必须收集的信息**：
1. 错误发生时间（精确到分钟或小时）
2. 错误关键字或异常类型（如 `NumberFormatException`）
3. 涉及的类名或方法名（如果有）
4. traceId（如果有，最精确）

**可选信息**：
- 服务器IP
- 错误发生的业务场景
- 相关参数值

> **信息不足规则**：如果用户未提供时间/关键字/traceId中的至少一项，必须主动询问。

### 第三步：查询线上日志

使用对应服务的日志查询技能连接线上服务器：

```
调用 [service-name]-log-query skill
- 尽可能缩小时间范围（先窄后宽）
- 提供异常关键字/类名
- 获取关键日志上下文（异常堆栈前后10行左右）
```

**通用日志查询要点**：
- 时间范围：首次查询控制在 30 分钟内，无结果再逐步扩大
- 关键字优先级：traceId > 异常类名 > 业务关键字 > 方法名
- 多服务器环境：两台服务器都要查（如 10.40.17.5 和 10.40.17.6）
- 注意区分应用日志和系统日志

### 第四步：查询相关代码

**代码定位策略**：
1. 根据日志中的类名和方法名定位代码
2. 根据错误类型推测可能出问题的代码位置（如 NumberFormatException → 类型转换/字符串解析）
3. 搜索调用链，理解数据流向

**搜索示例**：
```bash
# 搜索特定类
grep -r "ClassName" /path/to/project --include="*.java"

# 搜索特定方法
grep -r "methodName" /path/to/project --include="*.java"
```

**代码分析要点**：
- 关注异常的 catch 块，看是否有吞异常的情况
- 关注空指针可能的来源（未判空、上游返回 null）
- 关注类型转换的合理性（字符串转数字、Long 转 Integer 等）

### 第五步：根因分析

**分析框架**：

1. **错误定位**
   - 错误发生的代码位置（类:行号）
   - 错误类型和异常信息

2. **数据流分析**
   - 输入数据是什么（请求参数、MQ消息、定时任务触发）
   - 代码如何处理这些数据
   - 问题出在哪个环节

3. **根因确定**
   - 直接原因：代码层面的具体问题（如未判空、类型转换错误）
   - 根本原因：设计/逻辑层面的问题（如边界情况未覆盖、数据兼容性问题）

### 第六步：制定解决方案

**方案三要素**：

| 要素 | 说明 |
|------|------|
| 修复方案 | 具体如何修改代码，给出代码变更 |
| 验证方案 | 如何验证修复有效 |
| 预防措施 | 如何避免类似问题再次发生 |

## 异常类型速查表

| 异常类型 | 常见原因 | 排查方向 |
|---------|---------|---------|
| NullPointerException | 对象未初始化、上游返回 null | 找 null 来源，加判空，查调用方 |
| NumberFormatException | 字符串转数字失败 | 找入参值，检查数据合法性校验 |
| IndexOutOfBoundsException | 集合/数组越界 | 检查下标计算逻辑，List 判空判 size |
| ClassCastException | 类型转换错误 | 检查泛型/RPC反序列化类型 |
| IllegalArgumentException | 参数不合法 | 检查参数校验逻辑 |
| TimeoutException | 调用超时 | 检查 DSF 超时配置、下游服务响应时间 |
| IllegalArgumentException | 参数不合法 | 检查参数校验逻辑 |

## 信息不足处理规则

### 必须主动询问的场景
- 没有提供错误发生的时间（或时间范围太宽泛）
- 没有提供错误关键字或异常类型
- 没有提供 traceId 且无法通过其他方式定位
- 日志查询结果为空，需要扩大范围但不确定方向

## 任务超时打断机制

**时间阈值**：10分钟（从任务开始计时）

**触发处理**：
1. 立即暂停排查
2. 向用户汇报进展（已排查内容、当前发现、待排查方向）
3. 询问用户是否继续、是否有更多信息、是否调整策略

**汇报模板**：
```
【任务超时提醒】
当前问题诊断已持续超过10分钟，汇报进展如下：

**已排查内容**：
- [已排查的内容1]
- [已排查的内容2]

**当前发现**：
- [已发现的线索]

**待排查方向**：
- [还未排查的方向]

请确认：
1. 是否有更多相关信息可以提供？
2. 是否继续当前排查方向？
3. 是否需要调整排查策略？
```

## 核心原则

1. **必须交付根因**：不能只描述现象，必须找到根本原因
2. **必须给出解决方案**：每个诊断都必须有可行的解决方案
3. **结合日志和代码**：不能只看日志或只看代码，要综合分析
4. **逐步排查**：复杂问题分步骤排查，不要跳跃
5. **验证假设**：对推测的根因要验证，不能凭空猜测
6. **信息不足及时询问**：不要在没有足够信息的情况下盲目排查
7. **超时主动汇报**：超过10分钟必须主动汇报进展

## 参考示例

### 场景：NumberFormatException

**问题**：线上日志出现 `NumberFormatException: For input string: "all"`

**排查思路**：
1. 查日志定位到 `CommonUtil.collectionConvertor` 方法
2. 找到调用方 `AiRecruitBizModelBiz` 第96行
3. 分析发现逻辑判断有缺陷，未正确处理包含 "all" 的混合字符串
4. 修复：调整解析逻辑，先检查是否为纯 "all" 再执行数字解析
